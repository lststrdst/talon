# SCIM 2.0 и синхронизация идентичностей

## Контракт интеграции

Зафиксируй цепочку от источника до приложения, например `AD DS → IdP → SCIM → приложение`. Уточни, кто управляет каждым атрибутом, где работают SCIM-клиент и сервер, какой коннектор и версия установлены или какой профиль SaaS включён. Зафиксируй область выборки по OU, группам, назначениям и фильтрам. Проверь прямое и вложенное членство, правила для существующих учётных записей и условия выхода из области синхронизации. SCIM управляет жизненным циклом ресурсов. Вход, выдачу ролей и поведение активных сессий подтверждай проверками приложения. [SCIM Core Schema](https://www.rfc-editor.org/rfc/rfc7643.html) · [SCIM в Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/scim-support-in-entra-id)

Сверь поддерживаемые возможности с документацией поставщика и доступными `/ServiceProviderConfig`, `/ResourceTypes` и `/Schemas`. Проверь базовый URL, TLS, способ аутентификации, минимальные права токена, методы и расширения схемы. Уточни поддержку `/Users`, `/Groups`, изменения членства, фильтров, PATCH, типов пагинации и условных запросов по ETag. Для облачного коннектора сверь фактический формат запросов с его документацией. [SCIM Protocol §4](https://www.rfc-editor.org/rfc/rfc7644.html#section-4) · [Контракт Microsoft Entra для SCIM endpoint](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)

## Сопоставление и чтение

- Для каждого сопоставления запиши источник и цель, тип, преобразование, обязательность, правила для пустого значения и применение при создании или обновлении. Проверь приоритет атрибутов сопоставления и стабильность ключа при переименовании. `id` назначает SCIM-сервер. `externalId` передаёт клиент в своём пространстве идентификаторов, его уникальность на стороне сервера следует проверить отдельно. Меняемые имена и почту используй как ключ только при подтверждённой уникальности и понятном сценарии переименования. [SCIM Core Schema §3.1](https://www.rfc-editor.org/rfc/rfc7643.html#section-3.1) · [Настройка сопоставления в Microsoft Entra](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/customize-application-attributes)
- Проверь точный фильтр коннектора, например `userName eq "pilot.user@example.invalid"`, с корректным URL-кодированием значения параметра. Для поиска по ключу проверь ответы с нулём, одним и несколькими совпадениями. При неоднозначности выясни причину до записи. Для стандартной индексной пагинации сверь `startIndex` (первый индекс 1), `count`, `itemsPerPage`, `totalResults` и реальный набор `Resources` на страницах. При поддержке курсоров используй `nextCursor` до его отсутствия и сохраняй остальные параметры запроса. Тестируй с числом записей больше одной страницы. При обходе изменяемых данных учитывай возможность дублей или пропусков. [SCIM Protocol §3.4.2](https://www.rfc-editor.org/rfc/rfc7644.html#section-3.4.2) · [RFC 9865](https://www.rfc-editor.org/rfc/rfc9865.html)

## Запись, повторы и отключение

- Повторный цикл с тем же входом должен сохранять тот же объект и состав групп. При тайм-ауте создания или конфликте уникальности сначала проверь результат по стабильному ключу и сверь найденный ресурс перед новой записью. Для изменений применяй поддерживаемый PATCH, сохраняй поля вне области управления коннектора и сверяй состояние после неопределённого результата запроса. Если стороны поддерживают условные изменения по ETag, используй `If-Match` и повторно считывай ресурс при конфликте версии. Для `429` и временных сбоев соблюдай правила клиента и `Retry-After` при наличии. [Создание ресурсов](https://www.rfc-editor.org/rfc/rfc7644.html#section-3.3) · [Изменение ресурсов](https://www.rfc-editor.org/rfc/rfc7644.html#section-3.5) · [Версионирование](https://www.rfc-editor.org/rfc/rfc7644.html#section-3.14) · [HTTP 429](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)
- Согласуй ожидаемый результат отключения или удаления источника, снятия назначения и выхода из фильтра. Определи, когда цель получает `active: false`, когда снимается членство и когда используется `DELETE`. Проверь фактическую блокировку доступа, судьбу активных сессий, повторное включение того же ресурса и сохранность данных. Для массовых изменений сначала проверь ожидаемое число затронутых объектов и настрой доступный порог защиты от случайных удалений. [Атрибут active](https://www.rfc-editor.org/rfc/rfc7643.html#section-4.1.1) · [Удаление ресурсов](https://www.rfc-editor.org/rfc/rfc7644.html#section-3.6) · [Предотвращение случайных удалений в Microsoft Entra](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/accidental-deletions)

## Проверка на стенде

1. Используй отдельный тестовый tenant или экземпляр приложения, отдельный секрет и синтетических пользователей и группы. Начни с предварительного просмотра изменений, если коннектор его поддерживает, и проверь один объект вне области. Команды on-demand и автоматические валидаторы могут создавать, менять и удалять объекты в указанном endpoint. [Проверка по запросу в Microsoft Entra](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/provision-on-demand) · [Microsoft Entra SCIM Validator](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/scim-validator-tutorial)
2. Проверь создание, привязку существующего объекта, обновление, переименование, добавление и снятие членства, повтор прогона, выход из области и повторное включение. Проверь, как коннектор обрабатывает неоднозначное сопоставление или ошибку записи. Сверь состояние ресурса на цели и фактический доступ пользователя.
3. Сопоставь время цикла, идентификатор задания или корреляции, статус HTTP или действие в журнале коннектора и состояние источника и цели. Сохраняй только нужные поля. Очищай журналы от токенов, реальных данных пользователей и полных тел запросов. Отметь, какие проверки прошли через фактический коннектор и какие выполнялись только на тестовом SCIM endpoint. [Циклы Microsoft Entra provisioning](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/how-provisioning-works)
