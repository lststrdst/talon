# Talon · Git

Выполняй команды Git в терминале рантайма или через его инструмент запуска команд. Если инструмент доступен через уполномоченного исполнителя, передай ему путь проекта, нужную операцию и её критерий проверки. Если в среде нет Git или запуска команд, укажи, какие действия остались невыполненными.

## Проверь рабочую копию

Определи нужный проект и сверяй рабочую копию, включая linked worktree и вложенные репозитории. В примерах `repo` обозначает проверенный путь. Перед изменением ветки или индекса посмотри состояние, рабочий diff, staged diff и список новых файлов. Содержимое новых файлов проверяй отдельно, если они относятся к задаче.

```sh
git -C "$repo" rev-parse --show-toplevel
git -C "$repo" status --short --branch
git -C "$repo" --no-pager diff
git -C "$repo" --no-pager diff --cached
```

Для компактной сводки используй [context.py](scripts/context.py) на Python 3.9+. Помощник работает локально и возвращает JSON с корнем, веткой, состоянием файлов, upstream и эффективными данными автора и коммитера. Данные upstream относятся к уже полученным локальным ссылкам. Перед новым коммитом добавь `--require-identity`, чтобы запросить наличие данных в обеих ролях.

```sh
python3 "$talon_git_dir/scripts/context.py" --repo "$repo"
```

`talon_git_dir` — каталог этого навыка. Помощник игнорирует `GIT_DIR`, `GIT_INDEX_FILE` и другие перенаправления репозитория, отключает внешние фильтры и пропускает правки внутри submodule. Если задача использует отдельный индекс, переопределённый Git-каталог или внешние фильтры, сверяй нужный контекст штатными командами Git. Они также доступны в среде без Python.

Для новой ветки используй `git -C "$repo" switch -c "$branch" "$base"` после проверки точки старта. Если в репозитории ещё нет коммитов, укажи только имя ветки. Для существующей ветки используй `git -C "$repo" switch "$branch"`. В Codex используй префикс `codex/`, если пользователь или проект не задал другой. Сверь, что текущие изменения должны перейти на выбранную ветку. При detached HEAD или занятой ветке уточни исходную точку по состоянию репозитория и правилам задачи. В Codex создавай отдельный worktree через инструмент приложения, когда он нужен.

## Подготовь и проверь коммит

У нового коммита проверь автора и коммитера по профилю из инструкций пользователя или проекта. При `cherry-pick` и `rebase` сохраняй исходного автора, проверяй его в итоговом коммите и сверяй коммитера с профилем пользователя. Учти требования к подписи коммитов.

Для настройки одного репозитория с явно заданным профилем используй `git -C "$repo" config --local user.name "$name"` и `git -C "$repo" config --local user.email "$email"`. При расхождении проверь `git config --show-origin --show-scope --get-regexp '^(user|author|committer)\.(name|email)$'` и переопределения от `GIT_AUTHOR_*`, `GIT_COMMITTER_*` и `EMAIL`. GitHub связывает коммиты с аккаунтом по подтверждённому адресу пользователя или выданному GitHub адресу `noreply`. Учётная запись для push определяется отдельно. [Настройка email для коммитов в GitHub](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address)

- Добавляй нужные файлы через `git add -- "$path"` или отдельные фрагменты через `git add -p -- "$path"`. Перед коммитом сверяй весь индекс с помощью `git diff --cached` и сохраняй рабочие и staged-изменения вне задачи. Если такие staged-изменения есть только в других файлах, а нужные файлы целиком входят в задачу, проверь их полную разницу с `HEAD` и используй `git commit --only -m "$message" -- "$path"` с нужными путями. Если индекс содержит и нужные, и посторонние изменения, а в коммит должны попасть лишь отдельные фрагменты файла, собери нужные изменения в отдельном worktree, когда это соответствует цели, или согласуй разделение индекса.
- Когда индекс содержит только изменения по задаче, выполни обычный коммит. После него проверь SHA, фактические данные автора и коммитера, список файлов и остаток изменений через `git status`.

```sh
git -C "$repo" var GIT_AUTHOR_IDENT
git -C "$repo" var GIT_COMMITTER_IDENT
git -C "$repo" diff --cached --check
git -C "$repo" commit -m "$message"
git -C "$repo" log -1 --format='%H%nAuthor: %an <%ae>%nCommitter: %cn <%ce>' --name-status
git -C "$repo" status --short --branch
```

## Сверь и опубликуй ветку

Если задача включает синхронизацию, проверь нужный remote, целевую ветку и адреса чтения и записи через `git remote get-url` и `git remote get-url --push --all`. Скрывай учётные данные при выводе адресов. Для существующей удалённой ветки получи её точную ссылку и после успешного `fetch` сравни историю. В выводе `rev-list` первое число — коммиты только на серверной стороне, второе — только в `HEAD`. Для новой ветки сначала подтверди отсутствие ссылки через `git ls-remote --exit-code`. Код 2 означает отсутствие совпадений. При ошибке доступа проверь соединение или авторизацию.

```sh
git -C "$repo" fetch "$remote" "refs/heads/$branch"
git -C "$repo" rev-list --left-right --count FETCH_HEAD...HEAD
```

Если задача включает обновление ветки, применяй fast-forward, merge или rebase по результату сравнения и правилам проекта. Повтори проверку после обновления. Публикуй только в рамках задачи. Укажи целевой ref явно и после успешного push сравни полный локальный SHA с SHA опубликованной ссылки. Если адрес записи отличается от адреса чтения, проверяй опубликованную ссылку на сервере записи.

```sh
git -C "$repo" push "$remote" "HEAD:refs/heads/$branch"
git -C "$repo" rev-parse HEAD
git -C "$repo" ls-remote --exit-code "$remote" "refs/heads/$branch"
```

## Разреши конфликт

Определи текущую операцию через `git status`, найди конфликтные файлы через `git diff --name-only --diff-filter=U` и проверь смысл изменений с обеих сторон. Добавь только разрешённые файлы, проверь staged diff и запусти подходящие проверки проекта. Продолжи той же операцией через `git merge --continue`, `git rebase --continue` или `git cherry-pick --continue`. Если прерванная операция принадлежит пользователю или требуемое разрешение неясно, сохрани состояние и укажи, какое решение требуется. `reset --hard`, `clean`, перезапись истории и принудительная публикация требуют явного разрешения на соответствующее действие.
