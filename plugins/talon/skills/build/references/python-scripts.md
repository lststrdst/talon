# Разработка и проверка Python-скриптов

Когда пользователь просит написать или исправить скрипт, реализуй его и сам запусти доступные проверки. Определи обычную команду запуска, входы, ожидаемый результат и значимый отказ. В существующем проекте возьми поддерживаемые версии Python, окружение, зависимости и тестовые команды из `pyproject.toml`, документации и CI. Для отдельного скрипта зафиксируй версию, на которой он реально проверен, и требования к запуску.

## Напиши скрипт

- Для нового CLI с параметрами используй `argparse` или принятый в проекте парсер. Собери разбор параметров и вызов логики в `main(argv=None)`, а код завершения передай через `raise SystemExit(main())` под `if __name__ == "__main__"`. Сохраняй действующий CLI-контракт при изменении скрипта. Возвращай результат через stdout или файл, диагностику направляй в stderr и назначай ненулевой код ожидаемым ошибкам.
- Используй `pathlib.Path` и явно определи базу относительных путей. Для текстового ввода и вывода задай кодировку по контракту, например `encoding="utf-8"`. При обработке файлов проверь значимые для сценария пробелы, Unicode и недоступные пути.
- Держи преобразование данных отдельно от файловых, сетевых и системных операций, чтобы его можно было проверить в локальном окружении. Для административной записи учитывай текущее состояние, повторный запуск и частичный сбой. Внешние изменения проверяй на разрешённом тестовом ресурсе.
- Если скрипт вызывает внешнюю программу, передавай в `subprocess.run` список аргументов с `shell=False` и задай таймаут. Для ограниченного диагностического вывода используй `capture_output=True` и подходящую кодировку при чтении текста. Применяй `check=True`, когда успех обозначается только кодом 0. Для утилит со своим набором допустимых кодов сверяй `returncode` с их контрактом. Указывай контекст ожидаемой ошибки или таймаута без вывода секретов.

## Выполни проверки

1. Проверь активный интерпретатор и его версию. Запусти целевые существующие тесты и обязательные команды проекта через его окружение. Например, если проект использует pytest, выполни `python -m pytest tests/test_script.py` с настоящим путём. Для unittest используй команду проекта или `python -m unittest discover -s tests`. Проверь, что тесты действительно обнаружены и выполнены.
2. При отсутствии подходящего теста проведи локальный smoke через обычную точку входа. Создай синтетический ввод и выход во временном каталоге и подставь безопасные значения переменных окружения. Проверь код завершения, нужные поля stdout или stderr и содержимое выходного файла. Для скрипта с записью проверь повтор и состояние после значимого отказа. Если команда зависит от внешнего процесса или сервиса, используй стаб либо мок с проверкой вызова и результата.
3. При падении воспроизведи его на минимальном входе, локализуй причину по фактическому выводу и состоянию. Исправь причину в рамках задачи и повтори исходную проверку и затронутые тесты. Если полный прогон блокирует среда, выполни доступные локальные проверки и укажи, какая среда нужна для оставшегося сценария.

Для короткой проверки с ограничением времени можешь использовать [verify.py](../scripts/verify.py) из каталога навыка. После `--` передай действующую тестовую команду отдельными аргументами.

```sh
python3 "$talon_skill_dir/scripts/verify.py" --label python-tests --timeout 60 \
  -- python3 -m unittest discover -s tests
```

Задай `talon_skill_dir` абсолютным путём к каталогу навыка. Для smoke с известным маркером добавь `--expect MARKER` до разделителя `--`. `PASS` означает нулевой код и наличие маркера, если он задан. `FAIL`, `TIMEOUT` и `NOT_RUN` различают провал условия, превышение времени и ошибку запуска. Помощник печатает сводку без сырых stdout и stderr. Для разбора сбоя используй очищенный вывод штатного раннера. После таймаута сначала проверь состояние запущенных команд и удалённых операций, поскольку таймаут ограничивает непосредственный процесс.

Сообщи точную команду и версию Python, код завершения, число выполненных тестов либо проверенный вход и наблюдаемый выход. Для проверки с подменой назови зависимость и проверенный контракт. Утверждение о работе с реальным удалённым ресурсом требует запуска на разрешённом стенде и наблюдения его результата.

- [Python argparse](https://docs.python.org/3/library/argparse.html), [pathlib](https://docs.python.org/3/library/pathlib.html) и [subprocess](https://docs.python.org/3/library/subprocess.html)
- [Запуск pytest](https://docs.pytest.org/en/stable/how-to/usage.html) и [Python unittest](https://docs.python.org/3/library/unittest.html)
