# Разработка PowerShell

Начни с точки запуска, поддерживаемых версий и действующего runner проекта. Укажи Windows PowerShell 5.1 или PowerShell 7, разрядность процесса, нужные модули, субъект запуска и наблюдаемый результат. Для совместимости с 5.1 сохраняй поддерживаемый им синтаксис и API. Парсер PowerShell 7 проверяет только свою версию языка. Для нового модуля задай экспортируемые функции и требования в манифесте, а для существующего сохраняй контракт вызывающего кода.

## Код и административные изменения

- Выделяй проверяемую логику из операций с файлами, реестром, задачами, службами и HTTP. Используй явные параметры, проверку входов и объекты результата. Для диагностики используй потоки Verbose, Information или Error, сохраняя в выходном pipeline данные результата. Импорт модуля должен подготавливать функции без запуска административного сценария.
- Разрешай пути относительно `$PSScriptRoot` или явного параметра. Для точного пути используй `-LiteralPath`, где он поддерживается. Перед привилегированной записью проверяй целевой путь, владельца и ACL, включая reparse points. Конфигурацию и резервные копии сохраняй с нужным доступом службы.
- Для идемпотентности прочитай состояние, вычисли минимальное изменение и повторно прочитай результат. Второй запуск с теми же входами должен сохранить корректное состояние. Для одновременных запусков используй механизм блокировки или проверки версии, доступный системе. После таймаута с неизвестным исходом сначала сверяй состояние.
- Для изменяющей advanced-функции используй `[CmdletBinding(SupportsShouldProcess)]` и `$PSCmdlet.ShouldProcess(...)` вокруг каждой существенной записи, включая нативные программы. Проверяй `-WhatIf` отдельным тестом на отсутствие записей. Режим предварительного просмотра показывай как план изменения.
- Применяй `-ErrorAction Stop` на значимой границе отказа и обрабатывай ожидаемую ошибку с контекстом. Восстановление должно учитывать уже выполненные шаги и чужие изменения. Внешнюю программу вызывай через `& $executable @arguments`, проверяй `$LASTEXITCODE` сразу после вызова и учитывай документированные успешные коды этой программы. `Start-Process -Wait -PassThru` проверяй по `ExitCode`. Итоговый `exit` задавай во внешнем скрипте запуска, функции и модули возвращают результат или ошибку вызывающему коду.
- Для исходников с кириллицей, которые читает Windows PowerShell 5.1, используй UTF-8 с BOM. Для JSON, CSV, HTTP, логов и обмена с CMD выбери кодировку по контракту получателя. Значение `UTF8` у команд 5.1 и 7 отличается наличием BOM. Проверяй байты, чтение обратно, кавычки, переводы строк и Unicode-пути на каждой затронутой границе.

## Учитывай способ запуска

| Контекст | Что проверить на Windows |
| --- | --- |
| GPO | User или Computer scope, logon или startup, фактическую учётную запись, доступность сети и UNC, порядок применения и результат на пилотном устройстве. |
| Scheduled Task | Точный exe и аргументы, рабочую папку, триггер, logon type, права, политику параллельных запусков и повторов. Сверь историю, код завершения и конечное состояние. |
| Служба | Реальный service host, учётную запись, зависимости, запуск и остановку, восстановление после сбоя. Для скрипта укажи поддерживаемый механизм хостинга и его контракт. |

Для действий в сессии пользователя проверяй реальную активную сессию, UAC и отключённый RDP. Прогон от администратора в открытом терминале подтверждает только этот контекст. Секреты получай через принятый в проекте механизм без записи в аргументы, тестовые данные и журналы.

## Проверка перед передачей

1. Найди используемый проектом `powershell.exe` или `pwsh` и выполни существующие команды на целевых файлах. Определи версии через `$PSVersionTable`, `Get-Module -ListAvailable Pester,PSScriptAnalyzer` и `Get-Command Invoke-Pester -Syntax`. Используй доступные версии модулей с их фактическими параметрами.
2. Проверь синтаксис, PSScriptAnalyzer с настройками проекта и `Test-ModuleManifest` для изменённого модуля. Зафиксируй число проверенных файлов и находки. Для совместимости 5.1 используй доступные правила совместимости анализатора и реальный 5.1. Замечание анализатора разбирай по пути выполнения и контракту.
3. Запусти подходящие Pester-тесты в версии, которую использует проект. Для поддерживающих его версий `Invoke-Pester -Path ./tests -CI` даёт код отказа при проваленных тестах. Подстрой путь под репозиторий. Для существенного исправления проверь падение регрессии до патча и успех после. Подмени внешние операции, сверяй параметры, число вызовов и итоговые данные. В Pester 5 добавляй общий mock для опасной зависимости, если фильтрованные mocks иначе допускают реальный вызов.
4. Выполни нативный smoke на разрешённом Windows-стенде с нужными версиями, разрядностью и субъектом запуска. Выбери основной сценарий, повтор и значимый отказ, например отсутствие доступа, недоступный UNC или прерывание обновления. Проверь восстановление и сохранение защищённой конфигурации. Переносимую логику и mocks отчитай отдельно от нативного результата.

Передай в QA точную ревизию, контекст запуска, команды, коды завершения и наблюдаемое состояние. Для неподтверждённого сценария укажи конкретно недостающую среду или проверку. Подробные сценарии частичного отказа и установщика есть в [справочнике QA](../../qa/references/failure-testing.md).
