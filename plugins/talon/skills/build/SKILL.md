# Talon · Разработка

Выбери глубину по запросу. Для объяснения проследи фактический путь по коду и покажи точки входа, зависимости и места расширения. Для плана изучи контекст и предложи проверяемые шаги. Для реализации доведи согласованный сценарий до работающего изменения и проверь результат.

Для разбора связей в существующем проекте и содержательной правки используй [порядок работы с кодом](references/feature-work.md). Для скриптов, модулей, установщиков, GPO и служб Windows открой [руководство PowerShell](references/powershell.md) на этапе, который их затрагивает. Для простой правки достаточно ближайшего контракта, изменения и целевой проверки.

В незнакомом или смешанном проекте используй [Стек проекта](../stack/SKILL.md) для затронутого компонента. Найди его язык, конфигурацию и runner до реализации. Если они уже установлены в текущей задаче, повторный поиск не нужен.

Если проверка требует среды CI, временной БД, очереди или браузера, открой [Воспроизводимые проверки](../checks/SKILL.md) для нужного этапа.

Для многоэтапной фичи, существующей спецификации, изменения API или проверки затронутых пакетов используй [Сквозную разработку](../delivery/SKILL.md) для требований, ревью изменений или доказательств совместимости.

Для изменения AD DS, GPO, DNS и интеграции SCIM, в том числе YandexADSCIM, используй [проверки каталогов и Яндекса](../directory/SKILL.md) для затронутой среды.

- **Python.** Напиши скрипт, выполни подходящие тесты или запуск на временных данных и повтори проверку после исправлений. Используй [проверки Python-скриптов](references/python-scripts.md).
- **Серверы.** Для удалённого доступа используй [сценарий SSH](references/remote-ssh.md). Выбери [Windows Server](references/windows-server.md) или [Linux](references/linux-server.md) по среде. Сверь исходное состояние, выполни запрошенную операцию и проверь фактический эффект.

При прямом вызове Build в конкретном проекте применяй [память Talon](../go/references/project-memory.md) по умолчанию. Найди записи по текущему сценарию и сохрани полезный подтверждённый результат после реализации. Учитывай режим плана и явное отключение памяти.

Если работа упирается в серьёзную архитектурную развилку или рискованное изменение совместимости, примени [выбор модели](../go/references/models.md) к этому этапу.

## Выбери объём первой версии

1. Определи пользователя, его задачу и наблюдаемый результат. Для существующего проекта прочитай инструкции, найди нормальную точку входа, похожую реализацию и действующие команды проверки. Для нового проекта опирайся на ограничения пользователя и выбирай обратимые решения.
2. Предложи один первый сквозной сценарий. Он должен давать результат от реального входа до видимого выхода и проверяться на маленьком наборе данных. Вынеси второстепенные сценарии в следующий этап. Если ценность самой идеи сомнительна, предложи самый дешёвый способ проверить её до большой реализации.
3. Найди предпосылку, способную изменить весь план, например доступ к данным, поддерживаемую среду или внешний API. Проверь её раньше зависимой работы. Явно отмечай допущения, которые меняют решение. При развилке с заметными затратами дай одну рекомендацию и объясни, какое ограничение определило выбор.

Для карты незнакомого модуля или оценки влияния изменения на несколько компонентов используй локальный [Graphify](references/graphify.md), если требуется обзор связей. Начинай с конкретного символа или участка проекта.

Если причина или подход зависит от истории изменения, версии зависимости или upstream-исправления, открой [Поиск решений](../research/SKILL.md) и вернись к проверке в проекте.

Для нового интерфейса или изменения визуальной системы прочитай [режим дизайна](../design/SKILL.md) и передай в реализацию согласованные состояния и ограничения. Если по ходу реализации обнаружен конкретный пробел в доступных навыках по стеку или технологии, используй [Autoskills](../autoskills/SKILL.md), затем продолжи разработку.

## Разложи работу на шаги

- Расположи задачи по зависимостям и пользовательской ценности. Для каждого шага укажи действие, затронутый компонент или артефакт и наблюдаемый критерий готовности. Ориентир для плана небольшой задачи — несколько шагов, которые можно проверить по отдельности.
- Сначала проведи узкий рабочий сценарий через существующие границы, затем добавь ошибки, права, переход со старых данных и восстановление там, где это влияет на результат. Если сценарий удаляет или объединяет данные, явно назови правило и способ проверить результат до применения. Для рискованного изменения выдели отдельный эксперимент или пилот с критерием продолжения.
- Для сложного проекта поручай агентам независимые исследования, если это ускорит выбор архитектуры или проверку рисков. Передавай реализацию только с назначенными путями и согласованными контрактами. Объединяй результаты в один порядок действий.
- При реализации сверяй каждый значимый этап с критерием приёмки. Корректируй план по фактическому состоянию проекта. Для проверки исправления или готовности сборки передай версию, сценарии и условия приёмки в `$talon:qa`. Для запуска передай подтверждённые возможности, аудиторию и текущую стадию в `$talon:launch`.
- Перед итоговым ответом сохрани нестандартную проверку, которую удалось подтвердить и которая нужна повторно. Используй `.agents/talon/learned.md` или `.talon/learned.md`, если `.agents/` защищён. Сделай это сам, если память включена и задача допускает запись.

## Контракты, миграции и архитектурные решения

- На границе сервисов зафиксируй машиночитаемый контракт и переходи к [проверке совместимости](../delivery/references/compatibility-release.md). Учитывай используемые ошибки, пагинацию и уже развёрнутых клиентов.
- Для миграции данных установи, какие версии приложения будут работать одновременно. Проверь примеры старых данных, повтор заполнения после прерывания и наблюдаемый результат на тестовой БД. Если откат ограничен, проверь восстановление из копии. [Интеграционные проверки](../checks/references/integration.md)
- Для значимого архитектурного решения запиши ограничения, выбранный подход, рассмотренные варианты и условие, при котором решение нужно пересмотреть.

## Что выдать

Дай рекомендуемый первый шаг, затем упорядоченный план с зависимостями и критериями приёмки. Назови риски и решения, которые реально влияют на последовательность. Конкретизируй первый шаг до действия, которое можно начать сейчас. Сроки давай диапазоном с предпосылками, если пользователь их запросил и есть данные для оценки.
