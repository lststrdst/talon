# Talon · Тестирование

Веди задачу до проверяемого результата. На старте выясни ожидаемое поведение, затронутый сценарий и точную версию или состояние diff. Прочитай инструкции проекта. Ищи QA-плейбук в ссылках из `AGENTS.md`, документации по тестированию или README существующего QA-раннера. Используй существующий runner, сохраняй изменения пользователя и проверяй, что результаты относятся к итоговому коду.

Если риск затрагивает связи между модулями, используй [Graphify](../build/references/graphify.md) для поиска возможных вызывающих путей и выбора регрессий. Для нативных окон, меню, фокуса и системных диалогов прочитай [проверки с Agent Desktop](references/desktop-testing.md). Для скриптов и инфраструктуры Windows используй раздел проверки в [руководстве PowerShell](../build/references/powershell.md).

При браузерном сбое открывай [браузерные проверки](../checks/references/browser.md) для диагностики на странице и повторяемого теста. Если локальный прогон указывает на изменение зависимости или известный сбой раннера, используй [Поиск решений](../research/SKILL.md).

Для проверки Python-утилиты используй [сценарий Python](../build/references/python-scripts.md). Для API, службы или пакета на целевом сервере открой [Windows Server](../build/references/windows-server.md) или [Linux](../build/references/linux-server.md) и проверь фактическое состояние после запуска.

Если у проекта несколько языков или разных CI, используй [Стек проекта](../stack/SKILL.md) для каждой затронутой части. Сверяй команды с наличием файлов и целевой платформой. Подтверждай статус фактическим результатом каждого применимого прогона.

Для ревью ветки, проверки затронутых пакетов и результата CI на конкретной ревизии открой [Сквозную разработку](../delivery/SKILL.md).

Для проверки workflow CI, временных БД и очередей или подтверждения прогона по JUnit используй [Воспроизводимые проверки](../checks/SKILL.md). Для создания или прогона мобильного и веб-сценария открой [Сквозные тесты](../e2e/SKILL.md).

Для проверки политик, ответов DNS или синхронизации каталога открой [Каталоги, политики и Яндекс](../directory/SKILL.md). Сверь конфигурацию, применение и наблюдаемый эффект.

При прямом вызове QA в конкретном проекте применяй [память Talon](../go/references/project-memory.md) по умолчанию, если она не отключена. При аудите и проверке готовности используй её только для чтения без отдельного запроса на обновление. После проверенного исправления сохрани воспроизводимый способ проверки, если он пригодится в следующих задачах.

Для проверки действий модели в новом чате используй [задачи с независимой проверкой результата](../checks/references/agent-eval.md). Для ошибки из Sentry начни с [чтения события](../checks/references/sentry-readonly.md).

Для оценки структуры и инструкций навыка или плагина Codex используй [Plugin Eval](references/plugin-eval.md).

Для ревью визуального решения и доступности интерфейса используй [UI/UX Pro Max](../design/SKILL.md), затем подтверди выбранные критерии сценарием QA.

Если специальный тестовый стек или повторный сбой требует отсутствующего руководства, используй [Autoskills](../autoskills/SKILL.md), сохраняя режим аудита или исправления.

## Режим работы

- **Аудит** для «проверь», «найди баги», «покажи проблемы». Читай исходники, запускай проверки на изолированных данных, собирай доказательства. Файлы продукта и тестов доступны только для чтения. Побочные эффекты тестов ограничь временными артефактами и согласованным тестовым окружением.
- **Исправление** для «почини», «проверь и исправь». Воспроизведи дефект, внеси минимальную правку и проверь исходный сценарий и соседние варианты. Сохрани регрессию для существенного исправления, если существующие тесты её пропускают и новый тест можно надёжно воспроизвести.
- **Проверка релиза** для «можно выкатывать?», «проверь релиз». Проверь конкретный diff или сборку и назови обязательные проверки по рискам. Действия по публикации, деплою, изменениям production и внешним сообщениям определяются отдельным запросом и доступами.

## Команда

Текущий агент ведёт задачу, делегирует независимые части и сверяет доказательства. Для небольшой локальной правки выполни достаточную проверку без обязательной команды. Для широкого аудита, релиза или существенного изменения запусти отдельного специалиста по затронутой границе и назначь независимого ревьюера на итоговое состояние.

Перед запуском или повторным использованием подагента сверь [правило выбора модели](../go/references/models.md). Применяй его и при вызове общего агента взамен именованной роли.

| Роль | Задача |
| --- | --- |
| `talon-investigator` | Минимальное воспроизведение и проверка причины. |
| `talon-browser` | Пользовательские сценарии, роли, UI, сеть, Playwright. |
| `talon-e2e` | Создание и запуск регрессионных тестов через UI, мобильные сценарии Maestro, разбор падений раннера. |
| `talon-api` | HTTP-контракт, данные, повторы, гонки и частичный отказ. |
| `talon-windows` | PowerShell, установщик, обновление и нативный Windows. |
| `talon-infra` | Linux, SSH, проверка службы, пакета и серверных изменений. |
| `talon-fixer` | Локальная правка в назначенных файлах и целевая регрессия. |
| `talon-reviewer` | Независимая попытка опровергнуть исправление или готовность релиза. |

Выбирай только нужные роли и запускай независимые проверки параллельно в пределах доступных слотов. Ожидай результат только по идентификатору успешно запущенного подагента. Если именованный профиль недоступен, передай ту же задачу доступному подагенту с чёткой ролью и ограничениями. Если делегирование недоступно, выполни доступные проверки сам и зафиксируй, что независимая проверка отсутствует. Для командной работы и проверки релиза прочитай [регламент](references/team-workflow.md). Для конкретного риска прочитай подходящий раздел [сценариев отказа](references/failure-testing.md). Для выбора инструмента открой [справочник](references/toolbox.md).

## Проверки по типу риска

Для поиска пока неизвестного функционального дефекта выбери проверку по поведению в [каталоге тестов](../checks/SKILL.md). Там есть исполняемые шаблоны для преобразований данных, повторной отправки и клавиатурного фокуса, а также сценарий проверки самих тестов на изменённом условии.

- При потере ввода или состояния проследи действие, обработчик, подтверждённую запись, повторное чтение и возможные перезаписи.
- Для сравнения скорости измерь исходную и новую версии на одной фикстуре и в одинаковой среде. Укажи число прогонов, медиану и разброс.
- Перед релизом проверь, как команда заметит отказ и восстановит затронутый сценарий. Для n8n используй [тест workflow](../workflows/SKILL.md), для изображения в интерфейсе проверь [экспорт и рендер](../visuals/references/export.md).

## Что считать проверкой

1. Установи контракт и получи воспроизводимое отклонение. Для существенного исправления покажи, что один и тот же сценарий обнаруживает ошибку на исходном коде и проходит после правки. Если исходный прогон невозможен, укажи причину и уровень полученного доказательства.
2. Повтори сценарий на финальном состоянии и проверь подходящую негативную ветку. Добавь обязательные команды проекта по затронутой области. Не ослабляй ожидания теста и не объявляй повторный удачный прогон исправлением flaky-теста.
3. Проверяй на требуемой границе. Локальный HTML и mock дают частичное покрытие. Транзакцию, браузерный E2E, права службы и установщик подтверждай на подходящем стенде, сборке и ОС. В протоколе укажи среду, команду, результат и артефакт или причину пропуска.
4. Сверь итоговый diff и отчитайся о подтверждённых дефектах, исправлениях, доказательствах и пробелах. Для проверки релиза выдай один статус из регламента и перечисли условия, которые реально повлияли на решение. Если остались блокеры, укажи, какой снять первым и каким прогоном подтвердить результат. Храни сырой вывод приватно и удаляй из сводки секреты и персональные данные.
