# Выбор E2E-раннера

Определи поверхность сценария и найди рабочую команду в README, манифестах, конфигурации тестов и CI затронутого компонента. Начни с настроенного раннера, если он покрывает требуемое поведение. При нескольких наборах выбери тот, который запускает нужную сборку, роль, браузер или устройство. Подключай новый инструмент, если существующий набор не покрывает эту границу.

| Поверхность и признаки в проекте | Что запустить |
| --- | --- |
| Браузер, `playwright.config.*`, `@playwright/test` или команда Playwright в CI | Playwright. При отсутствии настроенного веб-раннера подходит для проверки DOM, навигации и браузерных проектов. Запусти конкретный spec и нужный `--project`, если проекты заданы. Например `npx playwright test tests/checkout.spec.ts --trace=retain-on-failure`. [CLI Playwright](https://playwright.dev/docs/test-cli) |
| Браузер, `cypress.config.*`, `cypress/e2e` и команда Cypress | Cypress E2E. Используй настроенный `baseUrl`, профиль браузера и spec из `specPattern`. Например `npx cypress run --e2e --spec cypress/e2e/checkout.cy.ts`. [CLI Cypress](https://docs.cypress.io/app/references/command-line) |
| Готовые Maestro Flow с `appId` для установленного Android/iOS-приложения или `url` для веб-сценария | Maestro. Выбери устройство или режим браузера по конфигурации проекта. Например `maestro test --format junit --output results.xml .maestro/checkout.yaml`. [CLI Maestro](https://docs.maestro.dev/maestro-cli/maestro-cli-commands-and-options) |
| Нативный или гибридный Android/iOS, настройки WebDriver с `appium:automationName` или отдельный Appium-набор | Appium. Для нового набора подходит, когда нужен WebDriver-клиент и доступ к нативному интерфейсу или WebView. Используй настроенный сервис или подними сервер `appium`. Выбери UiAutomator2 для Android или XCUITest для iOS и запусти тесты клиентской командой проекта. [Драйверы Appium](https://appium.io/docs/en/latest/ecosystem/drivers/) · [Пример JS-клиента](https://appium.io/docs/en/latest/quickstart/test-js/) |
| React Native с `detox.config.*`, `.detoxrc.*` или секцией `detox` в `package.json` | Detox. Для нового набора подходит при доступной тестовой сборке и необходимости синхронизации с приложением. Используй конфигурацию приложения и устройства из репозитория. Например `npx detox build -c ios.sim.release`, затем `npx detox test -c ios.sim.release`. [Подготовка Detox](https://wix.github.io/Detox/docs/introduction/project-setup/) · [CLI Detox](https://wix.github.io/Detox/docs/cli/test/) |
| Android с `androidTest` и Espresso либо iOS с UI Test target и тестовым планом Xcode | Сохрани платформенный набор. Android запускай настроенной задачей Gradle, например `./gradlew connectedDebugAndroidTest`. iOS запускай через `xcodebuild test` со схемой и назначением из проекта. [Тесты Android](https://developer.android.com/studio/test/command-line) · [XCTest](https://developer.apple.com/documentation/xctest/) |

Мобильный viewport браузера покрывает адаптивный веб-интерфейс. Для жестов, разрешений ОС, нативных экранов и переходов WebView выбери установленное приложение и подходящее устройство, эмулятор или симулятор. Сверь поддержку нужного поведения в выбранной среде.

## Агенты Playwright

Если среда предоставляет роли Playwright, подключай исполнителя для нужного этапа. Для одного короткого сценария достаточно одного тестера.

- `playwright_test_planner` исследует интерфейс и составляет план. Передай ему стартовую фикстуру и пользовательский результат.
- `playwright_test_generator` превращает выбранный пункт плана в исполняемый spec. Передай план, фикстуру и путь для записи.
- `playwright_test_healer` разбирает падение существующего теста. Если изменился локатор или устарели данные фикстуры, повтори тест с исходным ожиданием. При подтверждённом дефекте продукта сохрани падающий тест и trace. При приёмке сверяй, что нужный сценарий действительно выполнился.

Имена ролей зависят от рантайма. Для явной настройки в Codex команда соответствующей версии проекта — `npx playwright init-agents --loop=codex`. [Агенты Playwright](https://playwright.dev/docs/test-agents)

## Сценарий и доказательства

1. Зафиксируй сборку, точку входа, роль и начальное состояние. Используй штатную тестовую фикстуру и воспроизводимый запуск. Если готового сценария нет, напиши узкий тест, который выполняет пользовательское действие через интерфейс и проверяет наблюдаемый результат.
2. Проверь нужный эффект. После сохранения повторно открой запись или экран. Для меню и подсветок проверь попадание элемента в видимую область и возможность действия, если этого требует сценарий. Для мобильного интерфейса запиши ОС, устройство и состояние разрешений, которое влияет на результат.
3. Выполни тест с утверждениями и сверь код процесса, число выполненных, упавших и пропущенных проверок. Для повторяемого падения сохрани минимальный сценарий, ожидаемое и фактическое поведение, первое упавшее утверждение и подходящий артефакт. Это может быть trace Playwright, снимок Cypress, команды Maestro или снимок и лог мобильного раннера.
4. При исправлении повтори тот же тест с теми же условиями и утверждениями. Укажи, какая часть сценария проверялась на реальном приложении, а какая использовала синтетические данные или заглушки. Если среда отсутствует или ни один тест не выполнился, назови конкретное ограничение и укажи статус прогона.
