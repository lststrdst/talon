# Talon · Воспроизводимые проверки

Установи затронутый компонент, ревизию, команду и критерий результата. Начни с установленного раннера проекта. Выбери один нужный сценарий и переходи к другому только для отдельного риска.

| Что нужно подтвердить | Сценарий |
| --- | --- |
| Версию инструментов, команду из CI или корректность workflow | [Среда и CI](references/toolchain-ci.md) |
| Транзакцию, очередь, миграцию или эффект роли Ansible | [Интеграционные проверки](references/integration.md) |
| Пользовательское действие, ошибку UI или результат браузерного теста | [Браузерные проверки](references/browser.md) |
| Поведение приложения на устройстве или новый сквозной регрессионный тест | [Сквозные тесты](../e2e/SKILL.md) |
| Экспорт, импорт или преобразование теряет данные на редких сочетаниях | [Тесты свойств и граничных данных](references/property-tests.md) |
| Команда выполнена, ответ потерялся, пользователь повторил действие | [Повтор и дубли записей](references/retry-tests.md) |
| Диалог открывается мышью, но фокус теряется при работе с клавиатуры | [Клавиатурные сценарии](references/keyboard-tests.md) |
| Нужно выяснить, заметят ли существующие тесты ошибку в условии | [Мутационное тестирование](references/mutation-tests.md) |

Когда пользователь просит «найди баги», выбери пользовательский сценарий с конкретным риском и сформулируй ожидаемый результат. Подключи подходящий шаблон к функции, хранилищу или интерфейсу проекта. При аудите адаптируй тест во временной копии и используй изолированные данные. Если поручено добавить регрессию в проект, помести её в штатный набор и проверь обнаружение теста. В отчёте укажи, где выполнен тест и какие зависимости заменила фикстура.

Для запуска проверь условия в действующем манифесте, конфигурации и CI. Выбери подходящую среду, подготовь минимальную тестовую фикстуру, выполни команду и сверяй фактический результат с критерием. Инструмент нужен только там, где он закрывает конкретный пробел. Если зависимость или целевой раннер недоступны, выполни доступную часть и укажи границу результата.

При повторном отказе выдели первое ошибочное действие и его условия. Измени одну переменную, повтори узкую проверку и зафиксируй, повлияла ли она на результат. Для проверок отчётности один раз прогони известный ошибочный случай и убедись, что команда возвращает ошибку, а отчёт учитывает хотя бы один выполненный тест.

## Подтверди прогон

Назови рабочий каталог, фактическую команду, версию среды, код выхода и важное наблюдение. Для набора тестов укажи выполненные, упавшие и пропущенные тесты по отчёту раннера. Сборка, статический анализ и dry run имеют свои отдельные результаты. Если тесты не обнаружились или все были пропущены, зафиксируй отсутствие выполненных тестов.

Для раннера с JUnit используй `verify.py` из `build/scripts/` в Codex или `talon/scripts/` в переносимой сборке. Задай `talon_verify` абсолютным путём к помощнику. Для каждой проверки выбери новый путь отчёта во временном каталоге. Например, для репозитория с pytest:

```sh
talon_results=$(mktemp -d)
python3 "$talon_verify" --label unit --timeout 120 --junit "$talon_results/junit.xml" \
  -- python3 -m pytest --junitxml="$talon_results/junit.xml"
```

Помощник сверяет код выхода и свежий отчёт, считает тесты и возвращает JSON без сырых журналов и вывода тестов. Для разбора отказа используй очищенный вывод или один артефакт, относящийся к упавшей проверке. Для NUnit, TRX и других форматов используй штатную сводку их раннера. Сохраняй в памяти только способ повторить подтверждённую проверку и её условия.
