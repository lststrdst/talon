# Проверка операции после потери подтверждения

Выбери операцию, для которой повтор с тем же ключом должен сохранять один бизнес-результат. Например, создание заказа может завершиться до того, как вызывающая сторона получит подтверждение. Уточни, кто формирует ключ операции и что штатный повтор передаёт тот же ключ с теми же данными.

1. Создай отдельное тестовое хранилище. Вызови операцию по штатному пути записи. На тестовой границе ответа вызови ожидаемый сбой после подтверждённой записи и до того, как вызывающая сторона получит результат. Синхронизируй сбой с подтверждённым commit или завершением обработчика.
2. После сбоя отдельно перечитай сохранённое состояние. Проверь, что уже существует ровно одна запись с ожидаемыми ключом и данными. Сохрани её идентификатор для проверки повтора.
3. Повтори вызов с тем же ключом и данными. Если штатный клиент повторяет запрос сам, внедри сбой в его тестовый транспорт один раз и наблюдай штатный повтор. Ещё раз перечитай хранилище через отдельное соединение или независимый запрос. Сверь количество и идентификатор записей, содержимое и ответ повтора по контракту проекта.
4. Если одинаковые данные допустимы в двух самостоятельных операциях, отправь их с разными ключами. Проверь, что обе записи сохранились. При известном дефекте выполни один и тот же тест на версии с дефектом и после правки. Падение должно показать нарушение контракта, например расхождение между двумя сохранёнными строками и ожидаемой одной.

## Шаблон для Python

Скопируй [retry_contract.py](../assets/retry/retry_contract.py) в тесты проекта под именем `test_retry.py`, чтобы его подхватил штатный поиск тестов. Добавь рядом `retry_fixture.py` и подключи в нём реальную операцию проекта и её хранилище в изолированной тестовой среде. Шаблон использует стандартный `unittest` и временный каталог для каждого теста.

| Функция адаптера | Ожидаемое поведение |
| --- | --- |
| `create_store(path)` | Создаёт пустое хранилище для текущего теста. |
| `submit_order(path, operation_key, item, *, acknowledge=None)` | Выполняет штатную операцию и возвращает идентификатор заказа. Если передан `acknowledge`, вызывает его с идентификатором после завершения записи, до возврата результата вызывающей стороне. Исключение из `acknowledge` доходит до теста. |
| `read_orders(path)` | Через отдельное соединение читает все сохранённые заказы текущего теста и возвращает список кортежей `(order_id, operation_key, item)`. |

Шаблон моделирует последовательный повтор после потери ответа в одном процессе. Если защита от дубликатов должна сохраняться после перезапуска, повтори вызов через заново запущенный сервис с тем же тестовым хранилищем и проверь записи через независимое соединение. Для конкурентной обработки, повторной доставки очередью или поведения сетевого клиента выбери соответствующую интеграционную проверку. В отчёте укажи место сбоя, состояние до повтора и после него, а также код выхода и число выполненных, упавших и пропущенных тестов.

## Пример на SQLite

В каталоге с `retry_contract.py` и [example_store.py](../assets/retry/example_store.py) выполни команду. Она скопирует готовый адаптер в одноразовый каталог и запустит оба теста.

```sh
(
  set -e
  talon_retry_demo=$(mktemp -d)
  cp retry_contract.py "$talon_retry_demo/"
  cp example_store.py "$talon_retry_demo/retry_fixture.py"
  python3 "$talon_retry_demo/retry_contract.py" -v
)
```
