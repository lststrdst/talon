# Команды проекта и локальная проверка CI

## Найди команду по файлам

1. Определи корень и рабочий каталог затронутого компонента. В Git начни с `git ls-files -- <путь-компонента>` и учти новые манифесты текущей задачи. Прочитай проектные инструкции и CI для этого пути. В GitHub Actions начни с рабочей папки и shell шага, затем смотри настройки задания и workflow. Сверь `runs-on`, матрицу версий и вызовы локальных скриптов или reusable workflow. [Синтаксис GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)
2. Прочитай определения задач и вложенных локальных файлов как текст. Найди точное имя команды, зависимости, условия запуска и требуемые инструменты. Сопоставь её с командой из инструкции или CI. При нескольких раннерах выбирай по использованию в этом компоненте. Динамические имена и удалённые включения отмечай как требующие подтверждения.
3. На этапе чтения достаточно путей, объявленных имён и версий. Проверяй вывод `--list`, `--summary` и `--dry` по документации установленной версии перед их применением. Эти режимы у некоторых инструментов выполняют шаблоны, импорты или команды для вычисления значений.

## Используй раннер проекта

- **mise.** Ищи `mise.toml`, `.mise.toml`, `.mise/config.toml` или `.config/mise.toml`, разделы `[tools]` и `[tasks]`, `mise.lock` и каталоги задач вроде `mise-tasks/`. Один `.tool-versions` подтверждает наличие списка версий. Читай локальные включения и файлы задач как текст, поскольку mise может выполнять шаблоны при их загрузке. Если установленная версия поддерживает безопасный режим, для уточнения списка можно задать `MISE_SAFE=1` в окружении процесса и выполнить `mise tasks ls --local --json`. Сверь путь определения в выводе, поскольку учитываются и родительские каталоги. Для выбранной задачи используй `mise run <задача>` после просмотра конфигурации и зависимостей. Команда может установить недостающий инструмент. На Windows проверь `run_windows`, `shell` или выбор файла задачи. По умолчанию команды из TOML запускает `cmd /c`. [Конфигурация](https://mise.jdx.dev/configuration.html) · [Список задач](https://mise.jdx.dev/cli/tasks/ls.html) · [Безопасный режим](https://mise.jdx.dev/security.html#safe-mode) · [Файлы задач и Windows](https://mise.jdx.dev/tasks/file-tasks.html)
- **just.** Ищи `justfile` или `.justfile` с любым регистром имени и просмотри `import` и `mod`. Укажи точный путь, например `just --justfile <файл> --list` или `just --justfile <файл> --show <рецепт>`. Для прогона вызови `just --justfile <файл> <рецепт>`. На Windows сверяй настройки рецепта, наличие `sh` или выбранного PowerShell и внешних утилит. [Поиск justfile](https://just.systems/man/en/quick-start.html) · [Просмотр рецептов](https://just.systems/man/en/listing-available-recipes.html) · [Оболочки](https://just.systems/man/en/prerequisites.html)
- **Task.** Ищи `Taskfile.yml`, `Taskfile.yaml` и варианты `.dist` с этими расширениями. Читай `tasks`, `includes`, `deps`, `dir` и `platforms`. После проверки включений и вычисляемых полей можно уточнить список через `task --taskfile <файл> --list-all --json`. Подготовка списка может вычислить динамические переменные `sh` при настройке `dotenv`. `--dry` также может запустить эти переменные. Для прогона используй `task --taskfile <файл> <задача>`. На Windows проверь `platforms` и доступность команд, вызванных из Taskfile. [Поиск и запуск](https://taskfile.dev/docs/guide/running-tasks) · [Инициализация списка](https://github.com/go-task/task/blob/v3.54.0/setup.go#L217-L230) · [Платформы](https://taskfile.dev/docs/guide/platforms)
- **uv и Nox.** `pyproject.toml` вместе с `uv.lock` указывает на проектное окружение uv. `uv lock --check` проверяет актуальность lock-файла. `uv run --locked <команда>` сохраняет lock-файл и при необходимости синхронизирует окружение. Если окружение уже подготовлено и его синхронизация не нужна, используй `--no-sync`. Для `noxfile.py` при чтении найди функции с `@nox.session` и параметры. `nox --list` импортирует и исполняет файл Python, поэтому применяй его после просмотра файла и его импортов. Запускай выбранный сеанс через `nox -s <сеанс>` или `uv run --locked nox -s <сеанс>`, если Nox входит в окружение проекта. [Lock и синхронизация uv](https://docs.astral.sh/uv/concepts/projects/sync/) · [CLI Nox](https://nox.thea.codes/en/latest/usage.html) · [Загрузка Noxfile](https://github.com/wntrblm/nox/blob/main/nox/tasks.py#L79-L92)

Для повторного прогона используй те же рабочую папку, версию раннера, зафиксированные версии инструментов и зависимостей, ОС и оболочку. `mise.lock` фиксирует инструменты, а `uv.lock` фиксирует зависимости проекта. Уточни интерпретатор и зависимости, которые Nox устанавливает внутри каждого сеанса. [Lock-файл mise](https://mise.jdx.dev/dev-tools/mise-lock.html) · [Окружения Nox](https://nox.thea.codes/en/latest/config.html)

## Проверь GitHub Actions локально

- Для статической проверки выбранного workflow используй `actionlint .github/workflows/<файл>`. Когда нужно ограничиться проверками самого actionlint, поставь `-shellcheck= -pyflakes=` перед путём файла. Такой результат покрывает синтаксис и поддерживаемые проверки выражений и связей workflow. [Руководство actionlint](https://github.com/rhysd/actionlint/blob/main/docs/usage.md)
- Если нужна локальная репетиция Linux-задания и доступен Docker, просмотри `.actrc`, `needs`, используемые actions и команды задания. Выбери файл, задание и событие, например `act -W .github/workflows/ci.yml -j test pull_request`. Используй тестовые входные данные и окружение с доступами, необходимыми только для этого прогона. Для статического списка событий и заданий читай YAML напрямую. `act --list` может обращаться к Docker и читать настройки окружения и секретов даже без выполнения заданий. [Руководство act](https://nektosact.com/usage/) · [Инициализация act](https://github.com/nektos/act/blob/v0.2.98/cmd/root.go#L377-L429)
- Результаты act относятся к выбранному контейнеру, событию и конфигурации. Для интерфейса Windows, установщика, GPO или платформенного поведения используй соответствующий Windows-стенд или штатный runner. Например, `-P windows-latest=-self-hosted` запускает задание прямо на подходящем Windows-хосте. Для возможностей GitHub вроде OIDC и ограничений `permissions` опирайся на результат штатного CI. [Среды act](https://nektosact.com/usage/runners.html) · [Ограничения act](https://nektosact.com/not_supported.html)
