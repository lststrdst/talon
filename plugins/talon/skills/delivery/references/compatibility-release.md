# Совместимость и готовность выпуска

## Проверь изменённый контракт

- **OpenAPI.** Возьми спецификацию поддерживаемой версии и кандидата. Укажи точные SHA и пути. Если спецификации генерируются, получи обе штатной командой в соответствующих ревизиях. Для репозитория с установленным oasdiff и обеими спецификациями в Git используй, например, `oasdiff breaking "$base_sha:api/openapi.yaml" "$head_sha:api/openapi.yaml" --fail-on ERR --format json`. Для локально сгенерированных спецификаций передай пути к файлам. Сохрани отчёт, код выхода и выбранный порог. Разбери отдельно несовместимое изменение и ошибку чтения или разбора спецификации. Для локальной проверки используй локальные ссылки `$ref` и оставь загрузку внешних ссылок и публикацию отчёта отключёнными. Сравнение схем подтверждает заявленный контракт. Поведение API подтверди штатным интеграционным тестом. [oasdiff CLI](https://www.oasdiff.com/docs/getting-started) · [Аргументы с Git-ревизиями](https://www.oasdiff.com/docs/free-review) · [Порог и ссылки](https://www.oasdiff.com/docs/github-action)
- **Pact.** Если проект ведёт Pact Broker, сопоставь версию кандидата с версией опубликованного контракта или результата верификации. Проверь, что в Broker актуальны версии потребителей и поставщиков в целевой среде. Получи вердикт `pact-broker can-i-deploy --pacticipant "$service" --version "$candidate_version" --to-environment "$environment"`. Сохрани вердикт и ссылку на матрицу. Отсутствующие результаты верификации оставляют совместимость неподтверждённой. `--dry-run` годится для отладки запроса, поскольку его код выхода всегда успешен. `record-deployment` обновляет состояние Broker после фактически завершённого развёртывания и относится к штатной процедуре выпуска. [Pact Can I Deploy](https://docs.pact.io/pact_broker/can_i_deploy) · [Учёт развёртываний](https://docs.pact.io/pact_broker/recording_deployments_and_releases)

## Сверь версию и артефакт

- **Changesets.** Если проект уже использует `.changeset/config.json`, вызови проектный `changeset status --since "$base_sha" --output "$status_file"` перед `version`. Сверь ожидаемые пакеты, типы повышения версии и записи для журнала изменений. При отсутствии changeset для изменённых пакетов разберись с политикой проекта. Путь для JSON выбери во временном каталоге. [Changesets CLI](https://changesets.dev/guide/cli#status)
- **Release Please.** Если проект уже использует его workflow или manifest, проверь существующий release PR, версии и журнал изменений. При наличии CLI и настроенного доступа `release-please release-pr --repo-url "$repo" --target-branch "$release_branch" --token "$token_file" --dry-run` показывает предполагаемые операции для ветки удалённого репозитория. Сопоставь её SHA с проверяемой ревизией. Для `token_file` используй абсолютный путь к защищённому файлу токена, переданному проектом. [Предпросмотр Release Please](https://github.com/googleapis/release-please/blob/main/docs/troubleshooting.md#debugging-with-the-cli) · [Чтение токена из файла](https://github.com/googleapis/release-please/blob/main/src/util/coerce-option.ts)

Привяжи решение о готовности к согласованным коммитам, точному SHA кандидата и артефакту сборки с версией и хешем или digest. Перед публикацией, merge, созданием тегов или деплоем сверяй полномочия задачи и условия проекта. Для уже выполненного развёртывания подтверди фактическую версию в целевой среде через метаданные сервиса или digest установленного артефакта. Повтори контрольный сценарий на этой версии и укажи результат. При отсутствии доступа к среде зафиксируй, до какой точки подтверждён выпуск.
