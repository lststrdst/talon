# Системный код и сборка

Начни с каталога компонента и команды из CI или документации. Сверь версию инструментов, целевую ОС и архитектуру. Отдельно зафиксируй результаты проверки исходников, сборки и запуска в целевой среде.

## Shell и Linux

- Определи интерпретатор по shebang и фактической команде вызова. Для Bash используй `bash -n`, для POSIX shell — `sh -n`, для BusyBox ash — `busybox ash -n` в совместимой сборке BusyBox. Запусти ShellCheck с диалектом проекта, если он доступен. На временных данных проверь коды завершения, повторный запуск и поведение при частичном отказе. Для BusyBox сверь наличие applet-команд и их опций в целевом образе. [ShellCheck](https://github.com/koalaman/shellcheck)
- Проверяй unit-файлы через `systemd-analyze verify` в совместимой Linux-среде. Для Nginx используй `nginx -t` с тестовой конфигурацией и доступными файлами, на которые она ссылается. Запуск службы, права, перезапуск и наблюдаемый ответ проверь отдельным прогоном на согласованном стенде с подходящим init и версиями ПО. [systemd](https://www.freedesktop.org/software/systemd/man/latest/systemd-analyze.html), [Nginx](https://nginx.org/en/docs/switches.html)

## OpenWrt, QWRT и LuCI

1. Сверь ветку прошивки, выпуск, target/subtarget, профиль устройства и feeds. В рецепте `Makefile` найди зависимости, команды установки и файлы пакета. Для сборки пакета возьми SDK от подходящего выпуска и цели, затем используй цель Make из проекта. Для образа выбери предусмотренный проектом Image Builder или полную сборку. [SDK OpenWrt](https://openwrt.org/docs/guide-developer/obtain.firmware.sdk), [Image Builder](https://git.openwrt.org/openwrt/openwrt/tree/target/imagebuilder/Config.in)
2. При зависимости от Lua 5.1 запускай проверки этим интерпретатором. Для JavaScript используй тесты проекта, затем проверь загрузку LuCI, меню и обращения к API в браузере на тестовой прошивке. [LuCI JavaScript API](https://openwrt.github.io/luci/jsapi/index.html)
3. Проверь содержимое пакета или образа перед запуском. Эмулятор подходит для поддерживаемых образов и сервисных сценариев. Установку или обновление на устройстве, работу драйверов, радио и аппаратных интерфейсов проверяй на совместимом разрешённом устройстве. В отчёте укажи, до какого из этих этапов дошла проверка.

## Go

Применяй этот маршрут, когда у затронутого компонента есть `go.mod` или он входит в `go.work`. Сверь модуль и его ревизию с рецептом сборки. Исходники upstream, каталог сборки и checkout с правками могут относиться к разным ревизиям. Проверь директивы `go` и `toolchain`, затем сравни `go version` с CI. Запускай команды `go test` и `go build` из CI для нужного пакета. Сохраняй параметры `GOOS`, `GOARCH`, `CGO_ENABLED` и `-tags`, когда они влияют на выбор файлов. Для кросс-сборки укажи отдельно, где собран бинарник и где выполнены тесты. [Модули Go](https://go.dev/ref/mod), [параметры сборки и тестов](https://pkg.go.dev/cmd/go)

## Docker и Compose

Сверь Dockerfile, build context, платформу, базовые образы, Docker context и тестовый профиль Compose с CI. Используй согласованные тестовые конфиги и синтетические данные, отдельное имя проекта, собственные порты, сети и тома. Проверь mounts, внешние ресурсы и адреса зависимостей перед запуском. Для проверки объявленной конфигурации используй `docker compose config --quiet` с выбранным файлом и тестовым окружением. Сборку и проверку запуска выполняй на согласованном тестовом стенде. Останавливай и очищай только ресурсы этого прогона. [Проверка Compose](https://docs.docker.com/reference/cli/docker/compose/config/), [имя проекта](https://docs.docker.com/compose/how-tos/project-name/)
