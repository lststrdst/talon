# Windows-приложения и пакеты

- Определи точку входа и роль каждого файла. `.ps1` может загружать WinForms, System.Drawing или C# через `Add-Type`. `.cs` может быть самостоятельным лаунчером, а `.cmd` или `.vbs` могут запускать его без консоли. Проверь реальные аргументы, текущий каталог, кодировку, путь с пробелами и результат в фактическом контексте запуска.
- Уточни, нужен ли Windows PowerShell 5.1 или PowerShell 7, разрядность, рабочий стол пользователя, STA и модули. Если проект проверяет WinForms в Windows PowerShell 5.1 с STA, повтори именно эту среду. На другой ОС проверяй только переносимую логику, синтаксис и упаковку.
- При `.sln` или `.csproj` найди версию SDK, target framework, платформу и существующий способ сборки. Используй `dotnet build`, `dotnet test` или Visual Studio/MSBuild там, где это подтверждено конфигурацией. Для отдельного `.cs` найди существующий рецепт компиляции. При его отсутствии разбери контракт лаунчера и укажи недостающий шаг сборки.
- Найди скрипты проверки проекта. Сначала выполни его тест проверки пакета, AST или анализатор. Используй Pester, если есть его suite. Для сборки запускай тот же сценарий из свежей распаковки. Проверь наличие нужных файлов, непротиворечивые версии, запуск UI, события, повтор, восстановление и удаление по объёму задачи.
- Для службы, GPO или планировщика сверяй фактическую учетную запись и результат на согласованной Windows. Статическая проверка и запуск UI вручную покрывают свои границы. Запиши, какая версия пакета совпадает с исходниками и какие действия реально произошли на тестовом Windows.
