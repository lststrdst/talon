# JavaScript, TypeScript и веб

## Найди точку сборки

- Найди ближайший `package.json` и корень workspace. Сопоставь `packageManager`, `engines.node`, lock-файл и команды CI. `package-lock.json` указывает на npm, `pnpm-lock.yaml` и `pnpm-workspace.yaml` указывают на pnpm. Если признаки расходятся, уточни по CI и инструкциям проекта. В монорепозитории запускай проверку из workspace или пакета, как предусмотрено его конфигурацией.
- Проследи выбранные `scripts` до файлов и исполняемых зависимостей. Сверь версию Node с CI и контейнером. Для чистой установки с актуальным lock-файлом используй принятый в проекте режим, например `npm ci` или `pnpm install --frozen-lockfile`. [npm ci](https://github.com/npm/cli/blob/latest/docs/lib/content/commands/npm-ci.md), [pnpm install](https://pnpm.io/cli/install).
- Если файл запуска или тестовый файл, указанный в `scripts`, отсутствует, проверь корень запуска и полноту checkout. Если экспорт неполный, укажи, какая команда заблокирована и какого файла не хватает. Выполни доступные независимые проверки.

## Проверь изменённый сценарий

- **JavaScript и TypeScript.** Сверь ESM/CJS по `type`, расширениям и фактическому загрузчику. Определи тестовый раннер по `scripts` и конфигурации. Запусти существующие проверки типов, lint, сборку и целевые тесты по объёму правки. Для `node:test` используй принятые в проекте файлы или фильтр. [Раннер Node.js](https://nodejs.org/api/test.html).
- **React и Next.js.** Проверь маршрутизацию, границу серверных и клиентских компонентов и команду сборки по конфигурации. При наличии `next.config.*` и `vite.config.*` найди используемый плагин и точку запуска. Для адаптера на Vite, например vinext, сверяй поддержку задействованных API и поведение на целевом Node или edge-рантайме по его документации. [Компоненты Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components), [vinext](https://github.com/cloudflare/vinext).
- **Рендеринг и кеш.** Для затронутого маршрута проверь на собранном приложении первый ответ и переход внутри приложения. При SSR проверь HTML и гидратацию, при CSR дождись загрузки данных и проверь действие пользователя. Если менялись кеширование или данные, проверь повторный запрос и обновление результата после инвалидации с ожидаемыми заголовками. [Кеширование CDN в Next.js](https://nextjs.org/docs/app/guides/cdn-caching).
- **Node.js и Express.** Проследи путь от точки запуска через middleware и маршрут до ответа. Проверь запрос через существующий HTTP-тест или локальный экземпляр. Сверь код ответа, тело и ветку ошибок, которую могла затронуть правка. [Маршрутизация Express](https://expressjs.com/en/guide/routing/).
- **NestJS.** Найди модуль, контроллер, сервис и используемый HTTP-адаптер. Для изменения контракта запусти тест через приложение с действующими проверками входных данных. Для логики сервиса используй существующую тестовую конфигурацию зависимостей. [Тестирование NestJS](https://docs.nestjs.com/fundamentals/testing).
- **Расширение VS Code.** Сверь `main` или `browser`, `contributes` и условия активации в манифесте. Проверь команду в Extension Development Host или существующим интеграционным тестом в целевом хосте. [Тестирование расширений](https://code.visualstudio.com/api/working-with-extensions/testing-extension).
- **Статический сайт и PWA.** Проверь выдачу HTML, загрузку ресурсов и прямой вход по затронутым URL с путём публикации проекта. Если есть service worker, проверь первую загрузку, обновление кеша после новой версии и заявленное поведение без сети. [Service Worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers).

В результате укажи рабочий каталог, фактические команды, статус сборки и lint и, если раннер их сообщает, числа пройденных, упавших и пропущенных тестов. Отдельный запуск с нулём найденных тестов опиши как проверку поиска тестов. Для ручной проверки зафиксируй маршрут, действие и наблюдаемый результат.
